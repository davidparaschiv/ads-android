11. Schedule reminders — no extra broker

public.notification_jobs is the queue. Supabase scheduling calls the send-reminders worker, which sends FCM messages. RabbitMQ/Kafka are not required.

  1. Enable pg_cron and pg_net; ensure Vault is available.
  2. In Vault create rezerva_project_url: Supabase project HTTPS URL with no trailing slash.
  3. Create rezerva_cron_secret: exactly the existing Edge CRON_SECRET. Keep its value private.

Check first:

select jobid, jobname, schedule, active
from cron.job where jobname = 'rezerva-reminders';

Only if absent, run once in SQL Editor. This starts recurring processing of due jobs:

select cron.schedule('rezerva-reminders', '* * * * *', $job$
  select net.http_post(
    url := (select decrypted_secret from vault.decrypted_secrets
            where name = 'rezerva_project_url')
           || '/functions/v1/send-reminders',
    headers := jsonb_build_object(
      'Content-Type', 'application/json',
      'x-cron-secret', (select decrypted_secret from vault.decrypted_secrets
                        where name = 'rezerva_cron_secret')
    ),
    body := '{}'::jsonb,
    timeout_milliseconds := 10000
  );
$job$);

Read-only diagnostics:

select jobid, status, return_message, start_time
from cron.job_run_details order by start_time desc limit 10;
select id, status_code, timed_out, error_msg
from net._http_response order by created desc limit 10;
select id, send_at, status, attempts, last_error
from public.notification_jobs order by created_at desc limit 20;

A successful cron query does not prove HTTP success or phone delivery. Inspect HTTP status, Edge logs and the phone. Keep one schedule; paused projects cannot process reminders. Supabase scheduler pattern.

Push is best-effort, not an exact alarm. Register the phone token before testing; jobs without a token remain pending. Force-stopping Android, battery restrictions, invalid FCM credentials or a stopped scheduler can still prevent/delay delivery.

  3. Open the business home screen → Scanează programarea. Select the correct business and tap Scanează QR-ul clientului.
  4. Point the camera at the entire QR. The app opens current reservation details: business, service, calendar, customer name/email, date/time and status. Cancelled/completed/no-show reservations retain their real status; a scan never reactivates them.
  5. Try the same code as an unrelated company or a staff account without access to that calendar. Details must be refused. Revoking a staff invitation's access also blocks subsequent lookups.
  6. Cancel the scanner and scan again. Cancellation must not open an old result or change any booking.

An Android camera app that recognizes ro.rezerva.app://reservation?token=… can also open Rezerva. Sign-in and database checks still apply. The built-in scanner is the reliable app workflow; third-party camera apps differ in custom-link handling. It never opens arbitrary web URLs.

QR is a private lookup reference, not an identity document, payment proof or one-time admission ticket. Staff should check the returned customer, date and status. Both plans support read-only lookup; existing history stays readable under the same calendar permissions even after a plan expires. Only the actual booking customer can request its QR through the customer endpoint. Business staff do not get a “show QR” action.

Backend tests: local versus live

Local-only verification

npm run test:local
npm run check
npm run typecheck
npm run check:phone

test:local runs every tests/*.test.mjs, including in-process PostgreSQL/PGlite integration checks and mocked external/native contracts. No real provider credentials or paid messages are used. npm run test:qr runs the focused QR checks. test:backend:local includes the new QR database tests. JavaScript still uses @ts-check; no TypeScript app source was introduced.

Optional live harness — not run here

npm run test:backend:setup creates a private configuration from .env.backend.example, without overwriting existing settings. It is setup, not an integration test. If .env.backend.local already exists, manually rename its Twilio/Firebase entries; the setup command intentionally leaves them untouched.

A future deliberate live run requires a matching Supabase URL, public key and project ref, BACKEND_TEST_ENVIRONMENT=development, and explicit BACKEND_TEST_ENABLED=true. Use only recipients/accounts/devices and records you control.

Firebase's harness accepts either full JSON in GCLOUD_SERVICEACCOUNT_KEYS or a private JSON path in FIREBASE_SERVICE_ACCOUNT_FILE, never both. Example Windows path: C:/Users/David/private/firebase-service-account.json. Inline JSON in an env file must be one line enclosed in single quotes to preserve the JSON PEM \n escapes. FIREBASE_PROJID is required either way. Never source this file in Bash.

Do not run test:backend, test:backend:db, test:backend:all or live login/send/workflow commands for this local verification. They contact external services; some can create data or incur message charges and require explicit opt-in flags. Even read-only smoke is a live integration run.
